# Backend / Platform

하나의 백엔드 서버 안에서 공부 활동과 사용자 연결 기능을 담당하는 모듈입니다.
담당자는 팀에서 확정한 뒤 이 문서에 기록합니다.

## 담당 범위

- Study Session: 공부 세션 시작·종료와 기록
- Presence: 접속 및 활동 상태
- Discovery API: 사용자·활동 탐색에 필요한 API
- 백엔드 서버 전체의 배포와 프론트엔드 연동·통합

## 함께 정할 사항

- Account: 인증된 사용자 정보의 사용 방식, 공통 DB 스키마와 마이그레이션
- Focus: 타이머와 서버 공부 세션의 상태·시간을 맞추는 규칙
- Voyage: 접속 상태와 탐색 결과를 화면에 전달하는 데이터 형식
- 서버 공통: API 오류 형식, 환경변수, 배포 환경, 상태 확인 방식

서버 진입점과 환경변수, DB 연결은 `backend/`의 공통 구성을 사용합니다.
배포·통합 설정은 필요한 공통 위치에 두며, 이 폴더를 별도 서버나 배포 단위로 만들지 않습니다.

## Platform 상세 설계 — 2026-10-05

[설계 원본: 포커스로그 Notion](https://app.notion.com/p/3ef721888d7e80a288c3ddf7398f9221)의
StudySession, StudySession 데이터 구조, Presence, Discovery / Pass-by 토글을 통합한 설계입니다.
아래 내용은 구현 완료를 의미하지 않습니다. 코드·의존성·DB 변경은 별도의 구현 작업에서 진행합니다.
확정 사항을 본문에 정리하고, 보류된 기능과 아직 추천 단계인 구현 세부 사항은 문서 마지막에 구분합니다.

상단의 역할 소개를 구체화하면, 현재 Presence는 **공부 중 여부**를 계산하고 Discovery / Pass-by는
**항해 중 단방향 조우의 허용 여부**를 관리합니다. 계정 전체의 온라인 상태를 제공하는 기능은 현재 범위에 없습니다.

### 1. 역할과 공통 데이터 기준

| 영역                | 역할                                       | 저장 원본                               |
| ------------------- | ------------------------------------------ | --------------------------------------- |
| StudySession        | 세션 상태, 공부 기록, 담당 기기, 연결 확인 | `study_sessions`                        |
| DailyStudyRecord    | 사용자·서울 날짜별 누적 집중 시간          | `daily_study_records`                   |
| StudySessionRequest | 성공한 상태 변경 요청의 재실행 방지        | `study_session_requests`                |
| Presence            | 현재 공부 중 여부 조회                     | StudySession에서 계산, 별도 테이블 없음 |
| Discovery / Pass-by | 지속적인 조우 허용 설정                    | Account 사용자 설정의 `encounterMode`   |
| Encounter           | 단방향 조우의 대기·방문·종료와 세션별 로그 | 조우 한 건당 한 행                      |
| EncounterAvoidance  | 내가 특정 상대를 다시 만나지 않겠다는 설정 | 사용자 간 단방향 관계                   |

- PostgreSQL + TypeORM을 사용하며 Account와 동일한 NestJS 서버·공통 DB 연결을 사용합니다.
- 개발·운영 모두 `synchronize: false`로 두고 Migration으로 스키마를 변경합니다.
- DB 컬럼은 `snake_case`, TypeScript 속성은 `camelCase`를 사용합니다.
- 내부 사용자 ID는 `users.id uuid`, TypeScript에서는 `string`입니다. GitHub ID나 프로필 필드로 소유자를 식별하지 않습니다.
- 순간 시각은 UTC 기준 `timestamptz(3)`, 응답 시각은 UTC ISO 8601 문자열로 표현합니다. 날짜 구분·화면 표시는 `Asia/Seoul`, 날짜 경계는 서울 시간 `00:00`입니다.
- 집중 시간은 밀리초 정수 원본으로 계산·저장합니다. 표시할 때만 합산값을 초 단위로 반올림합니다. 반올림한 표시값끼리 합산하지 않습니다.
- 예: `600ms + 600ms = 1,200ms`를 저장하고 1초로 표시합니다. `1,500ms`는 2초로 표시합니다.
- 시간 판정과 기록 확정은 서버가 담당하고, 화면 타이머는 클라이언트가 표시합니다.

#### Account·Focus·Voyage 연동

- User/Auth/Profile과 사용자 설정은 Account 소유입니다. Platform은 합의한 `JwtAuthGuard`, `@CurrentUser()`, `AuthenticatedUser { userId: string }` 계약을 사용합니다. 실제 export 경로는 후속 구현에서 맞춥니다.
- body·query·path에 전달된 임의의 `userId`를 소유권 근거로 사용하지 않고 인증된 내부 사용자 ID를 검증합니다.
- Account의 `users` 생성 Migration 이후 Platform 외래키를 생성하며, 되돌릴 때는 의존성의 역순으로 처리합니다. 각 모듈은 담당 테이블의 Migration을 작성하고 연결·Migration 설정은 `backend/`에서 공유합니다.
- Focus는 화면 타이머·저장 대기 표시·서버 시각 보정을, Voyage는 조우 화면·방문·거절·pass 동작을 서버 계약에 맞춥니다.
- PostgreSQL의 트랜잭션·외래키·조건부 고유 인덱스로 관련 기록의 일관성을 관리하고, TypeORM으로 엔티티·Repository·Migration을 구성합니다.

### 2. StudySession 동작 규칙

#### 세션과 일별 기록

- 노트북·데스크톱을 대상으로 하며 사용자당 미종료 세션은 최대 하나, 그 세션을 제어하는 기기도 한 대입니다. 집중 중·일시정지·연결 끊김 후 유예 상태를 모두 미종료 세션에 포함합니다.
- 세션은 시작부터 명시적 중단 또는 재접속 유예 만료까지 이어집니다. 일시정지·재개는 같은 세션이며 휴식 시간은 집중 시간에서 제외합니다.
- 종료 후 다시 시작하면 같은 날이어도 새 세션입니다. 같은 날짜에 발생한 여러 세션의 집중 시간은 하나의 DailyStudyRecord에 합산합니다.
- 자정을 넘어도 세션을 유지합니다. 실제 집중 구간을 서울 시간 자정에서 나누어 각 날짜에 반영합니다.
- 세션 표시 이름은 최초 `startedAt`을 서울 시간 `YY/MM/DD - HH:mm`으로 변환합니다. 예: `26/10/04 - 13:26`. 이름은 저장하지 않으며 중복될 수 있으므로 식별에는 `id`를 사용합니다.
- 일시정지·재개·기기 전환·자정 통과는 이름, 최초 시작 시각, 세션 ID를 바꾸지 않습니다.

| 동작             | 집중 시간                          | 세션 상태                                          |
| ---------------- | ---------------------------------- | -------------------------------------------------- |
| 시작             | 해당 시각부터 시작                 | 기존 미종료 세션이 없을 때 새 `FOCUSING` 세션 생성 |
| 일시정지         | 유효한 현재 집중 구간 반영 후 멈춤 | 같은 세션의 `PAUSED`                               |
| 재개             | 해당 시각부터 다시 누적, 휴식 제외 | 같은 세션의 `FOCUSING`                             |
| 집중 중 중단     | 유효한 현재 집중 구간 반영 후 멈춤 | 바로 `ENDED`, 먼저 일시정지할 필요 없음            |
| 일시정지 중 중단 | 추가 누적 없음                     | `ENDED`                                            |
| 종료 후 시작     | 새로 누적                          | 새 세션 생성                                       |
| 자정 통과        | 날짜별로 나누어 반영               | 같은 세션 유지                                     |

화면 타이머는 매초 갱신합니다. 서버는 진행 중 **15초마다** 정상 확인된 집중 시간을 세션·일별 기록에 저장하고,
연결이 유효한 온라인 일시정지·중단·기기 전환 시에는 즉시 반영합니다. 화면의 날짜는 자정에 바뀌고,
DB는 다음 저장 시 실제 자정 기준으로 구간을 나눕니다.

예를 들어 10월 4일 23:40부터 10월 5일 00:20까지 집중하면 세션은 40분,
일별 기록은 각각 20분입니다. 23:55에 일시정지하고 00:10에 재개해 00:35에 중단하면
세션은 40분, 일별 기록은 각각 15분·25분입니다.

#### 연결 확인과 재접속 유예

- 담당 기기는 `FOCUSING`뿐 아니라 `PAUSED`에서도 **15초마다 heartbeat**를 보냅니다.
- 마지막 유효한 확인 후 **45초간** 추가 확인이 없으면 끊김으로 판단합니다. 정상 앱 종료 알림은 45초를 기다리지 않고 즉시 처리합니다.
- 연결이 유효한 정상 종료 알림이면 처리 시각까지 집중 시간을 반영합니다. 알림 없이 연결이 끊겼다면 마지막 서버 정상 확인 시점까지만 인정합니다.
- 끊김을 감지하면 `PAUSED`로 전환하고, **서버가 실제로 감지한 시각**을 `disconnectedAt`에 저장합니다. 유예 시작을 마지막 heartbeat 시각으로 소급하지 않습니다.
- 재접속 기한은 `disconnectedAt + 600초`입니다. 이 유예는 타이머 재개가 아니라 **기존 세션 재접속**을 위한 시간입니다. 단순 로그인과 구분합니다.
- 사용자·세션 잠금을 얻고 실제 처리할 차례가 된 서버 시각 `t`로 판정합니다. `t <= disconnectedAt + 600초`면 허용하고, 초과하면 자동 종료 후 거절합니다. 요청 도착 시각을 사용하지 않습니다.
- 재접속에 성공하면 유예를 해제하고 `PAUSED`로 복원합니다. 사용자가 재개해야 집중 시간을 누적하며, 이전 유예 때문에 나중에 다시 종료하지 않습니다.
- 감지 지연·오프라인·재접속 유예 시간은 집중 시간에 추가하지 않습니다. 유효하게 연결된 일반 휴식은 세션 종료 사유가 아닙니다.
- 자동 종료 후에는 새 세션을 시작합니다. 명시적으로 중단한 세션도 다시 열지 않습니다.

| 예시                                                     | 결과                                             |
| -------------------------------------------------------- | ------------------------------------------------ |
| 마지막 정상 확인 14:00:00, 끊김 감지 14:00:45            | 집중 시간은 14:00:00까지, 재접속 기한은 14:10:45 |
| 실제 재접속 처리 시각이 정확히 14:10:45                  | 재접속 허용, 일시정지 상태로 복원                |
| 기한 14:10:00, 요청 도착 14:09:59, 잠금 후 처리 14:10:01 | 재접속 거절                                      |

#### 기기 전환과 오프라인 조작

- 새 기기에서는 기존 세션을 확인한 뒤 **현재 기기로 같은 세션 가져오기 / 기존 기기에서 계속하기**를 선택합니다. 가져오기를 선택했을 때만 담당 기기를 변경합니다.
- 가져오기 후에도 세션·공부 기록을 유지하며 `PAUSED`로 넘깁니다. 이전 기기가 집중 중이었어도 자동 재개하지 않습니다.
- 이전 연결이 유효하면 전환 시각까지 집중 시간을 반영하고, 이미 만료됐다면 마지막 정상 확인까지만 유지합니다. 끊김 상태에서는 동일한 600초 재접속 기한을 적용합니다.
- 기기 제한은 세션 제어에 관한 규칙이며 계정 전체의 동시 로그인 차단을 뜻하지 않습니다. 기존 앱을 강제 종료할 필요는 없고, 제어 차단은 서버가 보장합니다.
- 오프라인에서는 새 세션 시작·재개를 허용하지 않습니다. 일시정지·중단은 화면 타이머를 즉시 멈추고 **저장 대기**로 표시합니다.
- 저장 대기 요청은 원래 `sessionId`, `controlToken`, 동일 `requestId`를 유지합니다. 연결 복구 후 만료·기기 전환 여부를 확인하며, 이미 종료됐거나 담당이 바뀐 세션에는 적용하지 않습니다.
- 로컬 타이머의 오프라인 경과 시간을 나중에 소급해 더하지 않습니다. 재접속·기기 전환으로 과거 상태나 종료된 세션을 되살리지 않습니다.

### 3. StudySession 데이터 구조와 처리

#### StudySession — `study_sessions`

| DB 컬럼                | TypeScript 속성      | PostgreSQL 자료형 | NULL / 기본값 / 의미                                                    |
| ---------------------- | -------------------- | ----------------- | ----------------------------------------------------------------------- |
| `id`                   | `id`                 | `uuid`            | NOT NULL, PK, `gen_random_uuid()`로 UUID v4 생성                        |
| `user_id`              | `userId`             | `uuid`            | NOT NULL, FK → `users.id`, `ON DELETE CASCADE`                          |
| `started_at`           | `startedAt`          | `timestamptz(3)`  | NOT NULL, 서버가 정한 최초 시작 시각                                    |
| `ended_at`             | `endedAt`            | `timestamptz(3)`  | NULL 허용, 기본 NULL, 종료 시각                                         |
| `status`               | `status`             | `varchar(16)`     | NOT NULL, 시작 시 `FOCUSING`, CHECK: `FOCUSING`, `PAUSED`, `ENDED`      |
| `focused_ms`           | `focusedMs`          | `bigint`          | NOT NULL, 기본 0, 세션 누적 집중 밀리초, 음수 금지                      |
| `deleted_at`           | `deletedAt`          | `timestamptz(3)`  | NULL 허용, 기본 NULL, 계정 탈퇴에 따른 소프트 삭제 시각                 |
| `last_heartbeat_at`    | `lastHeartbeatAt`    | `timestamptz(3)`  | NOT NULL, 시작 처리 시각으로 초기화, 마지막 유효한 연결 확인            |
| `disconnected_at`      | `disconnectedAt`     | `timestamptz(3)`  | NULL 허용, 기본 NULL, 서버가 끊김을 감지한 시각                         |
| `controller_device_id` | `controllerDeviceId` | `uuid`            | 미종료 시 필수, 종료 시 NULL, 앱 설치 단위 기기 ID                      |
| `control_token`        | `controlToken`       | `uuid`            | 미종료 시 필수, 종료 시 NULL, 서버가 발급한 제어 차수 ID                |
| `last_accrued_at`      | `lastAccruedAt`      | `timestamptz(3)`  | `FOCUSING`에서 필수, 그 외 NULL, 누적 반영한 구간의 끝 시각             |
| `last_heartbeat_seq`   | `lastHeartbeatSeq`   | `bigint`          | NOT NULL, 기본 0, 현재 토큰에서 처리한 마지막 heartbeat 순번, 음수 금지 |

- `ended_at IS NULL`인 행의 `user_id`에 조건부 고유 인덱스를 둡니다. 집중·일시정지·유예 상태 모두 사용자당 하나입니다.
- `FOCUSING`·`PAUSED`이면 `endedAt IS NULL`, `ENDED`이면 `endedAt IS NOT NULL`입니다. 종료 시각은 시작 시각 이상이어야 합니다.
- `FOCUSING`이면 `lastAccruedAt IS NOT NULL`이고 `disconnectedAt IS NULL`입니다. `PAUSED`·`ENDED`에서는 `lastAccruedAt IS NULL`입니다.
- `disconnectedAt`이 있으면 미종료 `PAUSED` 상태이며 `disconnectedAt >= lastHeartbeatAt`이어야 합니다.
- 미종료 세션은 유예 중에도 담당 기기·토큰을 유지합니다. 종료 시 `controllerDeviceId`, `controlToken`, `lastAccruedAt`, `disconnectedAt`을 NULL로 정리하고 `lastHeartbeatAt`은 남깁니다.
- `controllerDeviceId`는 클라이언트가 설치 단위로 생성·보관하는 UUID이며 재설치는 새 기기로 취급합니다. 기기 ID는 인증 수단이 아닙니다.
- `controlToken`은 시작·재접속·기기 전환 때 새 UUID v4로 교체합니다. JWT·로그인 토큰과 별개입니다. 새 토큰의 `lastHeartbeatSeq`는 0, 클라이언트 순번은 1부터 시작합니다.
- `lastHeartbeatSeq`는 TypeScript·JSON에서 정밀도를 잃지 않도록 십진 문자열로 주고받습니다.
- `heartbeatExpiresAt = lastHeartbeatAt + 45초`, `reconnectDeadlineAt = disconnectedAt + 600초`는 계산값입니다. 별도 컬럼을 만들지 않으며 `disconnectedAt`이 NULL이면 재접속 기한도 없습니다.

#### DailyStudyRecord — `daily_study_records`

| DB 컬럼      | TypeScript 속성 | PostgreSQL 자료형 | 제약 / 의미                                               |
| ------------ | --------------- | ----------------- | --------------------------------------------------------- |
| `user_id`    | `userId`        | `uuid`            | NOT NULL, 복합 PK, FK → `users.id`, `ON DELETE CASCADE`   |
| `study_date` | `studyDate`     | `date`            | NOT NULL, 복합 PK, 서울 날짜 예: `2026-10-04`             |
| `focused_ms` | `focusedMs`     | `bigint`          | NOT NULL, 기본 0, 해당 날짜의 누적 집중 밀리초, 음수 금지 |
| `deleted_at` | `deletedAt`     | `timestamptz(3)`  | NULL 허용, 기본 NULL, 소프트 삭제 시각                    |

복합 기본키는 `(user_id, study_date)`이며 별도 일별 기록 ID를 만들지 않습니다.

#### 집중 시간·트랜잭션·서버 시각

1. 세션 생성·변경·heartbeat·기기 전환·만료·탈퇴 연동은 **사용자 행 → 세션 행 → 날짜 오름차순의 일별 기록** 순서로 잠급니다. 사용자 잠금은 세션이 없는 상태에서의 동시 시작도 직렬화합니다.
2. 필요한 사용자·세션 잠금을 얻은 뒤 DB의 `clock_timestamp()`로 처리 기준 시각 `t`를 한 번 얻어 밀리초 정밀도로 통일합니다. 클라이언트 시각이나 트랜잭션 시작 시각인 `now()`를 대신 사용하지 않습니다.
3. 미종료 세션의 `disconnectedAt`이 NULL이고 `t >= lastHeartbeatAt + 45초`이면 연결을 갱신하기 전에 끊김을 처리합니다. 늦은 heartbeat만으로 집중 상태를 복구하지 않으며 명시적 재접속이 필요합니다.
4. 유효한 `FOCUSING` 상태에서는 `[lastAccruedAt, t)`를 세션에 더하고, 동일 구간을 서울 자정에서 나누어 일별 기록에도 더합니다.
5. 세션 상태·세션/일별 누적값·집계 기준 시각·연결 정보·성공 요청 기록을 같은 트랜잭션에서 저장합니다. 일부만 성공하면 전체를 롤백합니다.

- 집중 중 heartbeat는 누적 반영 후 `lastAccruedAt`, `lastHeartbeatAt`을 `t`로 갱신합니다. 일시정지 중 heartbeat는 연결 시각·순번만 갱신합니다.
- 시작·재개는 두 시각을 `t`로 설정합니다. 연결이 유효한 일시정지·중단·정상 종료 알림은 `t`까지 반영한 뒤 `lastAccruedAt`을 해제합니다. 세션 시작과 유효한 제어 요청도 연결 확인으로 취급합니다.
- 45초 무응답 감지 시에는 마지막 정상 확인 이후의 시간을 더하지 않고 누적값을 유지한 채 일시정지·끊김 상태로 전환합니다.
- 재접속 성공 시 `disconnectedAt = NULL`, 새 담당 기기·토큰, `lastHeartbeatAt = t`, `lastHeartbeatSeq = 0`, `PAUSED`로 설정합니다.
- 주기적인 만료 작업과 세션 요청 시 만료 확인을 함께 사용합니다. 만료 작업도 잠금 후 최신 값을 확인하므로 먼저 성공한 재접속을 과거 기한으로 종료하지 않습니다.
- StudySession 자동 종료의 `endedAt`은 실제 종료 전환 시각 `t`입니다. 작업 지연 시간은 집중 시간에 포함하지 않습니다.
- 서버 재시작 후에도 DB 시각으로 판정합니다. 서버 중단 전에 끊김을 감지하지 못했다면 재시작 후 실제 감지 시각부터 유예를 시작하며 마지막 heartbeat로 소급하지 않습니다.

#### 담당 기기 검증과 재시도

- 일반 제어 요청·heartbeat는 인증된 `userId`, `sessionId`, `controllerDeviceId`, `controlToken` 및 사용자·세션의 삭제 상태를 확인합니다.
- 재접속·가져오기는 소유자만 요청하며, 화면에서 확인했던 토큰을 `expectedControlToken`으로 전달합니다. 잠금 후 현재 값과 비교해 동시 요청 중 먼저 유효하게 처리된 요청만 성공시킵니다.
- 토큰 교체 후 이전 토큰의 heartbeat·일시정지·재개·중단은 현재 세션을 변경하지 못합니다. 앱 재실행도 재접속으로 새 토큰을 받습니다.
- `controlToken`은 소유자에게 필요한 제어 응답에만 포함합니다. 기기 ID나 제어 토큰만으로 사용자를 인증하지 않습니다.
- 시작·일시정지·재개·중단·정상 종료 알림·재접속·기기 전환은 클라이언트 UUID `requestId`를 사용합니다. 같은 동작의 재전송에는 같은 ID와 내용을 사용합니다.
- 재시도는 인증·삭제 상태 확인 후 기존 성공 기록을 먼저 확인합니다. 동일 `(userId, requestId)`와 동일 내용이면 원래 결과를 반환하고 상태·시간·연결 확인을 다시 변경하지 않습니다. 같은 ID에 다른 내용이면 충돌로 거절합니다.
- 성공 기록이 없는 새 요청에만 현재 토큰·상태 조건을 검사합니다. 이 순서로 재접속·기기 전환 자체의 재시도가 새 토큰 때문에 중복 실행되지 않게 합니다.
- 과거 성공 응답은 현재 상태를 복원하는 명령이 아닙니다. FE는 기기 전환·종료 등이 뒤따랐을 수 있으므로 최신 세션 상태를 확인합니다.
- heartbeat는 매번 요청 기록을 만들지 않습니다. 현재 토큰에 대해 `seq > lastHeartbeatSeq`인 경우만 처리하고, 같거나 작은 순번은 시간·연결 시각 모두 갱신하지 않습니다.
- 클라이언트는 상태 변경을 순서대로 보내고 응답 후 다음 상태 변경을 보냅니다. 실패한 heartbeat를 쌓아 재전송하지 않고 연결 복구 후 최신 세션 상태를 먼저 확인합니다.

#### StudySessionRequest — `study_session_requests`

공부 구간 이력이 아니라 성공한 상태 변경의 중복 실행을 막는 처리 기록입니다.

| DB 컬럼        | PostgreSQL 자료형 | 제약 / 의미                                                                               |
| -------------- | ----------------- | ----------------------------------------------------------------------------------------- |
| `user_id`      | `uuid`            | NOT NULL, 복합 PK, FK → `users.id`, `ON DELETE CASCADE`                                   |
| `request_id`   | `uuid`            | NOT NULL, 복합 PK, 사용자 범위에서 재사용하지 않는 요청 ID                                |
| `session_id`   | `uuid`            | NOT NULL, FK → `study_sessions.id`, `ON DELETE CASCADE`, 시작 요청도 생성된 세션 ID 기록  |
| `operation`    | `varchar(16)`     | NOT NULL, CHECK: `START`, `PAUSE`, `RESUME`, `END`, `DISCONNECT`, `RECONNECT`, `TAKEOVER` |
| `request_hash` | `char(64)`        | NOT NULL, 동작·대상·기기·제어 식별자 등 정규화한 요청 내용의 SHA-256                      |
| `result`       | `jsonb`           | NOT NULL, 성공 응답, 인증 토큰·불필요한 프로필 정보 제외                                  |
| `processed_at` | `timestamptz(3)`  | NOT NULL, 성공 처리에 사용한 서버 기준 시각                                               |

- PK는 `(user_id, request_id)`이며 요청 사용자와 세션 소유자 일치를 같은 트랜잭션에서 검증합니다.
- 상태 변경과 성공 기록 삽입을 함께 커밋합니다. 실패·롤백한 작업은 성공 기록을 남기지 않습니다.
- 기록은 세션과 함께 유지하고 사용자 또는 세션의 물리 삭제 때 CASCADE로 삭제합니다. 소프트 탈퇴 시에는 보존하되 삭제된 사용자·세션의 과거 결과를 일반 응답으로 제공하지 않습니다.

### 4. Presence

Presence는 조회 시 계산하는 **현재 공부 중 여부**입니다. 연결 정보는 StudySession에 두고,
별도 Presence 테이블·저장용 `isStudying`·접속 이력·삭제 컬럼을 만들지 않습니다.

#### 공부 중 판정

서버 판정 시각 `t`에 다음 조건을 모두 충족하면 `isStudying = true`입니다.

1. 사용자와 세션이 소프트 삭제되지 않았으며 해당 사용자의 미종료 세션입니다.
2. `status = FOCUSING`, `endedAt IS NULL`, `disconnectedAt IS NULL`입니다.
3. 현재 담당 기기와 `controlToken`이 설정돼 있습니다.
4. `t < lastHeartbeatAt + 45초`입니다.

일반적인 판정 조건을 충족하지 않으면 false입니다. 로그인만 한 경우, 세션 없음, 일시정지,
연결 만료, 재접속 유예, 재접속·기기 전환 직후, 종료를 모두 포함합니다.
삭제된 사용자·세션은 일반 조회 대상에서 제외합니다. **false를 계정의 오프라인 상태로 해석하지 않습니다.**

- 만료 작업이 늦어 저장된 상태가 아직 `FOCUSING`이어도 연결 기한이 지났다면 false입니다.
- 조회가 새 세션을 만들거나 heartbeat를 대신 갱신하지 않습니다. 서버 재시작 후에도 DB 상태와 시각으로 계산합니다.
- 공부 시간·세션 상태·제어 토큰을 Presence에 중복 저장하지 않습니다.

#### 조회 데이터

| 필드          | TypeScript / JSON                   | 의미                                                        |
| ------------- | ----------------------------------- | ----------------------------------------------------------- |
| `userId`      | `string` (UUID)                     | Account 내부 사용자 ID                                      |
| `isStudying`  | `boolean`                           | `evaluatedAt` 기준 공부 중 여부, 클라이언트가 설정하지 않음 |
| `evaluatedAt` | `string` (UTC ISO 8601)             | 서버 판정 시각                                              |
| `validUntil`  | `string` 또는 `null` (UTC ISO 8601) | true이면 `lastHeartbeatAt + 45초`, false이면 NULL           |

`validUntil`은 결과를 현재 상태처럼 사용할 수 있는 기한의 상한입니다. 그때까지 공부를 계속한다는 보장은 아닙니다.
서버 기준으로 보정한 시각을 사용하고, 기한이 지난 결과를 현재 공부 중 표시로 유지하지 않습니다.
기한 만료가 자동 재조회·구독을 뜻하지는 않습니다. `controllerDeviceId`, `controlToken`, `requestId`는 상대방에게 제공하지 않습니다.

#### 조회 권한과 시점

- 관리자는 관리자 권한으로 조회할 수 있으며 조우 관계를 요구하지 않습니다. 삭제 상태에 따른 조회 제외는 유지합니다.
- 일반 사용자는 서버가 확인한 단방향 조우의 **viewer → target** 방향으로 조우 시점에 조회합니다. 임의의 사용자 ID만으로 조회하거나 역방향 권한을 자동 부여하지 않습니다.
- 조우 시 최신 StudySession으로 계산한 결과를 전달합니다. 과거 조우 로그나 프로필 조회 권한만으로 현재 Presence를 계속 조회할 수 없습니다.
- 일반 화면의 상시 폴링·지속 구독·주기적 상대 상태 갱신, 관리자 자동 갱신 화면은 현재 요구에 포함하지 않습니다. 기존 타이머·15초 heartbeat와 구분합니다.
- 조회 실패와 서버가 판정한 false는 구분합니다. 실패를 공부하지 않는 상태로 간주하지 않으며, 이 구분을 위해 DB에 `UNKNOWN` 상태를 추가하지 않습니다.
- target의 공부·접속 여부는 조우 후보 자격이 아닙니다. viewer의 새 조우 시작 자격에는 `isStudying`을 사용합니다.
- 상대의 **접속 중 / 미접속 표시는 제공하지 않습니다.** `isOnline`, 별도 온라인 추적 테이블·구독을 추가하지 않습니다.

### 5. Discovery / Pass-by 설정과 후보

- Discovery는 조우 허용, Pass-by는 조우 비허용입니다. `FOCUSING`·`PAUSED`·`ENDED`와 별개이며 Pass-by에서도 공부 시간은 정상 누적될 수 있습니다.
- 계정 설정에 저장하고 다음 세션에도 유지합니다. 기본값은 `DISCOVERY`, 변경은 서버 저장 성공 시 현재 세션에도 즉시 적용합니다.
- StudySession에 모드를 복사하거나 별도 모드별 테이블·boolean을 만들지 않습니다. 재접속·기기 전환도 최신 계정 설정을 사용합니다.
- Discovery에서는 시스템이 자동으로 상대를 선정합니다. 발생 간격은 보류 상태입니다.

| 소유 영역           | DB 컬럼          | TypeScript 속성 | 자료형 / 제약                                                               |
| ------------------- | ---------------- | --------------- | --------------------------------------------------------------------------- |
| Account 사용자 설정 | `encounter_mode` | `encounterMode` | `varchar(16)`, NOT NULL, DEFAULT `DISCOVERY`, CHECK: `DISCOVERY`, `PASS_BY` |

설정 변경 권한은 인증된 본인에게 있습니다. 설정 테이블·Entity의 실제 이름은 Account 계약에서 맞춥니다.

#### 단방향 조우와 역할별 자격

| 구분   | 의미                               | 새 조우 자격                                                       |
| ------ | ---------------------------------- | ------------------------------------------------------------------ |
| viewer | 자신의 화면에서 조우를 보는 사용자 | 유효한 계정·세션, `DISCOVERY`, `isStudying = true`, 활성 조우 없음 |
| target | viewer의 화면에 나타나는 상대      | 유효하고 삭제되지 않은 계정, `DISCOVERY`                           |

- viewer의 자격 계산값은 `canStartEncounter`, target의 기본 자격 계산값은 `canAppearAsTarget`입니다. 서버 내부 계산값이며 DB에 저장하거나 다른 사용자에게 자동 공개하지 않습니다.
- target은 **최초 선정부터 미접속·일시정지·공부 종료·StudySession 없음 상태여도 가능합니다.** 연결·집중 여부로 같은 가중치 그룹 안에서 차등을 두지 않습니다.
- A 화면에 B가 나타나도 B 화면에 A를 자동 표시하지 않습니다. 역방향 조우는 별도 사건입니다. 자신과의 조우는 허용하지 않습니다.
- viewer가 일시정지·끊김·유예·종료 상태이면 새 조우를 시작하지 않습니다. 일시정지만으로 계정 모드를 Pass-by로 바꾸지는 않습니다.
- viewer 화면에는 대기·방문을 합쳐 **활성 조우 한 건**만 허용합니다. 유지 중인 상대를 새 상대가 자동 교체하지 않습니다.
- 같은 target이 여러 viewer 화면에 동시에 나타나는 것은 허용합니다. target에 대한 점유 제한은 없습니다.

선정 순서는 viewer 자격 확인 → target 계정·모드 자격 확인 → 자신·재조우 제한·다시 만나지 않기 제외 →
남은 후보 가중치 추첨 → 최신 조건 재검사 → 조우 확정입니다.
최종 재검사에서 자격을 잃은 후보를 억지로 확정하지 않고 후보를 다시 조회하거나 이번 시도를 건너뜁니다.

### 6. Encounter 체류와 데이터 구조

#### 방문·거절·pass

- 조우가 성립하면 방문·거절 선택을 기다립니다. 대기 기한은 `decisionDeadlineAt = encounteredAt + 600초`입니다.
- 10분 이내 방문을 선택하면 같은 Encounter의 `visitedAt`에 서버 수락 시각을 기록합니다. 새 조우나 별도 방문 테이블을 만들지 않습니다.
- **방문 후에는 10분 자동 pass를 적용하지 않습니다.** 사용자가 pass할 때까지 유지하되 아래의 다른 종료 사유가 먼저 발생하면 종료합니다.
- 방문 전 거절은 즉시 종료, 미선택은 10분이 지나면 자동 pass입니다.
- pass는 현재 상대를 떠나 항해를 계속하는 동작입니다. 계정의 Pass-by 전환이나 공부 세션 중단을 뜻하지 않습니다.
- 새로고침·재접속·기기 전환은 최초 대기 기한이나 `visitedAt`을 초기화하지 않습니다. 방문 선택은 재조우 제한의 기준 시각도 바꾸지 않습니다.
- 예: 14:00 조우 → 14:05 방문 → 14:10에도 체류 → 다른 종료 사유 없이 15:00 사용자 pass 시 종료합니다.

#### 진행 중 상태 변경

| 변경 / 요청                                    | 현재 조우 처리                                           |
| ---------------------------------------------- | -------------------------------------------------------- |
| viewer 일시정지·연결 끊김·기기 전환            | 유지, 대기 10분은 계속 흐름, 방문 상태 보존              |
| viewer 동일 세션 재접속                        | 아직 종료되지 않은 대기·방문 상태 복원, 기한 초기화 없음 |
| viewer StudySession 종료·유예 만료             | 대기·방문 모두 종료, 새 세션으로 옮기지 않음             |
| target 일시정지·미접속·공부 세션 종료          | 유지, target의 세션·접속은 체류 조건 아님                |
| viewer 또는 target의 Pass-by 전환              | 해당 사용자가 참여한 모든 활성 조우 종료                 |
| viewer가 현재 target에게 다시 만나지 않기 적용 | 해당 viewer → target 조우 즉시 종료                      |
| 방문 전 거절 / 방문 후 pass                    | 현재 조우 종료                                           |
| 미방문 상태로 선택 대기 10분 만료              | 자동 pass                                                |

A가 Pass-by로 전환하면 A가 viewer인 조우와 **A가 target인 다른 모든 화면의 활성 조우**를 끝냅니다.
모드가 서버에 반영되는 시각을 기준으로 일관되게 처리하며, 이 동작이 다른 사람의 StudySession을 종료하지는 않습니다.
Discovery로 다시 바꾸거나 화면 알림이 늦게 도착해도 종료된 조우는 되살리지 않습니다.

활성 조우가 끝난 뒤에만 다음 조우가 가능하며, 곧바로 다음 상대를 보여준다는 뜻은 아닙니다.
선택 기한을 넘긴 미방문 조우는 종료 작업이 지연돼도 활성으로 보지 않고, 새 조우 생성 전에 만료 조우를 정리합니다.
방문 체류 기한과 Presence의 `validUntil`은 별개이므로 체류가 길어져도 과거 Presence를 현재 상태로 계속 사용하지 않습니다.

#### Encounter 스키마

한 행을 현재 체류와 종료 후 세션별 로그에 함께 사용합니다. 체류용·이력용 테이블을 중복 생성하지 않습니다.

| DB 컬럼             | TypeScript 속성   | PostgreSQL 자료형 | 제약 / 의미                                              |
| ------------------- | ----------------- | ----------------- | -------------------------------------------------------- |
| `id`                | `id`              | `uuid`            | NOT NULL, PK, 서버가 생성하는 조우 사건 ID               |
| `viewer_session_id` | `viewerSessionId` | `uuid`            | NOT NULL, FK → `study_sessions.id`, `ON DELETE CASCADE`  |
| `target_user_id`    | `targetUserId`    | `uuid`            | NOT NULL, FK → `users.id`, `ON DELETE CASCADE`           |
| `encountered_at`    | `encounteredAt`   | `timestamptz(3)`  | NOT NULL, 최초 조우 성립 시각·대기 시작·재조우 제한 기준 |
| `visited_at`        | `visitedAt`       | `timestamptz(3)`  | NULL 허용, 기본 NULL, 방문 선택을 서버가 수락한 시각     |
| `ended_at`          | `endedAt`         | `timestamptz(3)`  | NULL 허용, 기본 NULL, 조우 종료 시각                     |

- viewer는 `viewerSessionId`가 가리키는 StudySession의 `userId`, target은 `targetUserId`로 식별하며 두 사용자는 달라야 합니다.
- 상대 세션을 가리키는 `targetSessionId`는 저장하지 않습니다. 상대가 새 세션을 시작해도 같은 계정과의 조우입니다.
- `visitedAt`은 체류 만료 시각이 아닙니다. NULL일 때만 대기 10분을 적용합니다. `decisionDeadlineAt`·`expiresAt`·`isVisited`·별도 방문 테이블은 저장하지 않습니다.
- `visitedAt`은 `encounteredAt` 이상이며 선택 기한 내의 시각입니다. 정확히 기한에 도달한 방문 요청의 처리 규칙은 마지막의 추천안에 구분합니다.
- `endedAt`이 있으면 `encounteredAt` 이상이어야 하며, 방문한 경우에는 `visitedAt` 이상이어야 합니다. 방문한 조우에는 `endedAt <= encounteredAt + 600초` 제약을 적용하지 않습니다.
- 미방문 조우는 선택 기한을 넘겨 종료 시각을 기록하지 않습니다. 지연된 자동 pass의 `endedAt`은 작업 실행 시각이 아닌 `decisionDeadlineAt`이고, 다른 종료 사유가 먼저 처리됐다면 그 더 이른 시각을 사용합니다.
- 방문·거절·pass·자동 만료·다시 만나지 않기·모드 변경은 같은 활성 조우에 대해 순서를 보장합니다. `visitedAt`이 유효하게 저장됐다면 이전에 예약된 10분 만료 작업으로 종료하지 않습니다.
- 재시도는 `visitedAt`을 다시 기록하거나 `endedAt`을 늦추거나 종료된 조우를 복원하지 않습니다.
- 새 조우 확정도 같은 viewer 기준으로 직렬화해 활성 조우 두 건을 막습니다. 모드 변경·사용자 지정 제외와 조우 종료/생성이 일관되게 처리돼야 합니다.
- 세션별 로그 인덱스는 `(viewer_session_id, encountered_at, id)`를 사용합니다. 같은 시각의 기록도 `id`로 순서를 구분합니다.

#### 세션별 조우 로그와 프로필

- 사용자는 세션 종료 후 해당 세션에서 만난 상대 목록을 볼 수 있습니다. 거절·자동 pass·방문 후 pass·다시 만나지 않기·Pass-by 전환 등 종료 사유와 관계없이 조우 행을 남깁니다.
- 방문 선택은 새 로그를 만들지 않고, 제한이 풀린 뒤 실제 재조우가 발생하면 별도 조우 행을 만듭니다.
- 인증된 사용자가 `viewerSessionId`의 소유자인지 검증합니다. 과거 로그 조회에 현재 세션의 `controlToken`을 요구하지 않습니다.
- 로그는 상대와 조우 시각을 확인하는 기록이며 상대의 현재 Presence를 계속 조회할 권한은 아닙니다.
- 조우 화면·과거 로그의 상대 정보 원본은 상대방 프로필입니다. 구체 필드와 표시 방식은 보류합니다.

### 7. 재조우 제한과 EncounterAvoidance

#### 자동 재조우 제한

- 한 번 조우한 상대는 **조우한 오늘과 내일** 제외합니다. `Asia/Seoul` 달력 날짜 기준이며 정확한 48시간 제한이 아닙니다.
- `cooldownUntil`은 해당 viewer가 target을 마지막으로 만난 `encounteredAt`의 서울 날짜에 2일을 더한 날의 `00:00`입니다. 서버 시각이 그보다 이르면 제외하고, 같거나 이후면 날짜 제한만 해제합니다.
- 같은 `viewerSessionId`에서 이미 만난 `targetUserId`는 세션이 끝날 때까지 제외합니다. 3일 이상 이어진 세션에도 적용합니다.
- 날짜 제한과 같은 세션 제한 중 **하나라도 남아 있으면 제외**합니다. 새 viewer 세션은 날짜 제한을, 새 target 세션은 어느 제한도 초기화하지 않습니다.
- 예: 10월 5일 만난 상대는 10월 7일 00:00 이후 새 세션에서는 후보가 될 수 있지만, 같은 세션이 계속되고 있다면 여전히 제외합니다.
- 날짜 제한은 viewer의 모든 세션을 통틀어 확인합니다. 과거 세션의 표시상 숨김·소프트 삭제만으로 제한을 지우지 않습니다.
- 이력은 단방향입니다. A가 B를 본 사실이 B가 A를 봤다는 뜻은 아닙니다.
- 별도의 직전 상대 제외는 두지 않습니다. 날짜·세션 제한이 모두 풀리면 마지막 상대도 다른 자격을 확인해 다시 후보가 될 수 있습니다.
- 제외 후 후보가 없으면 조우를 건너뛰고 항해를 계속합니다. 후보 확보를 위해 제한을 완화하지 않습니다.

#### 다시 만나지 않기

- A가 B를 지정하면 A 화면에서만 B를 후보에서 제외합니다. B가 A를 제외하지 않았다면 B는 자신의 자격·제한에 따라 A를 만날 수 있습니다.
- 계정 단위로 지속되며 세션 종료·날짜 경과로 자동 만료되지 않습니다. 가중치보다 먼저 적용합니다.
- 설정 당시 A 화면에 B가 대기·방문 중이면 해당 조우를 즉시 종료합니다. 이 설정만으로 B → A 방향의 조우까지 종료하지 않습니다.
- 개인 설정에서 해제할 수 있습니다. 해제는 앞으로의 사용자 지정 제외만 풀고 조우·날짜 제한·세션 제한·로그를 초기화하지 않습니다.
- 프로필·메시지 등 다른 기능의 일반 차단 정책으로 자동 확장하지 않습니다.

#### EncounterAvoidance 스키마

| DB 컬럼          | TypeScript 속성 | PostgreSQL 자료형 | 제약 / 의미                                                        |
| ---------------- | --------------- | ----------------- | ------------------------------------------------------------------ |
| `owner_user_id`  | `ownerUserId`   | `uuid`            | NOT NULL, 복합 PK, FK → `users.id`, `ON DELETE CASCADE`, 설정 주체 |
| `target_user_id` | `targetUserId`  | `uuid`            | NOT NULL, 복합 PK, FK → `users.id`, `ON DELETE CASCADE`, 제외 대상 |
| `created_at`     | `createdAt`     | `timestamptz(3)`  | NOT NULL, 서버 저장 시각                                           |

- PK는 `(owner_user_id, target_user_id)`, CHECK는 `owner_user_id <> target_user_id`입니다. 반복 설정 요청은 중복 행을 만들지 않습니다.
- A 후보 계산에는 `(ownerUserId = A, targetUserId = 후보)`만 확인합니다. 반대 방향 행을 자동 적용하지 않습니다.
- 해제는 인증된 owner가 소유한 해당 관계 행을 제거합니다. A의 해제가 B → A 관계까지 제거하면 안 됩니다.
- 자동 만료·해제 여부·소프트 삭제 컬럼이나 StudySession/Presence의 `isBlocked`를 추가하지 않습니다. 별도 변경 감사 이력은 현재 범위에 없습니다.
- 설정 저장과 현재 조우 종료를 일관되게 처리하고 새 조우 확정 때도 최신 설정을 확인합니다.

### 8. 초기 가중치 식 — 확정

모든 후보 자격과 제외 조건을 먼저 적용한 뒤 남은 **사용자 ID별 후보**를 추첨합니다.
`U`는 남은 미조우 후보 수, `R`은 남은 기조우 후보 수입니다.
`R`은 전체 가입자·온라인 사용자·제외된 사용자 수나 과거 만남 횟수가 아닙니다.

```text
미조우 한 명의 가중치 = R + 1
기조우 한 명의 가중치 = 1
전체 가중치 D = U × (R + 1) + R

미조우 한 명의 선택 확률 = (R + 1) / D
기조우 한 명의 선택 확률 = 1 / D
미조우 그룹 전체의 확률 = U × (R + 1) / D
기조우 그룹 전체의 확률 = R / D
```

| U   | R   | 미조우 한 명 가중치 | 기조우 한 명 가중치 | 미조우 그룹 확률 | 기조우 그룹 확률 |
| --- | --- | ------------------- | ------------------- | ---------------- | ---------------- |
| 1   | 1   | 2                   | 1                   | 66.67%           | 33.33%           |
| 3   | 2   | 3                   | 1                   | 81.82%           | 18.18%           |
| 5   | 5   | 6                   | 1                   | 85.71%           | 14.29%           |
| 1   | 99  | 100                 | 1                   | 50.25%           | 49.75%           |
| 0   | 4   | 해당 없음           | 1                   | 0%               | 100%, 각 25%     |

- 같은 그룹에서는 모두 같은 가중치를 갖습니다. 두 그룹의 총 가중치로 그룹을 먼저 뽑고 내부에서 균등 선택해도 동일한 확률입니다.
- 미조우 `1`, 기조우 `1 / (R + 1)`인 비율식과 동치이며 초기 적용은 정수식을 기준으로 합니다.
- 미조우가 한 명 이상이면 미조우 그룹 확률은 50%를 초과하지만 매번 새 상대를 보장하지 않습니다. `R + 1`은 기조우 전체 가중치 `R`보다 큰 가장 작은 정수입니다.
- 각 시도마다 최신 `R`로 다시 계산합니다. 과거 가중치에 곱하거나 만남 횟수마다 누적 감점하지 않으므로 반복 횟수 때문에 가중치가 0으로 수렴하지 않습니다.
- `U = 0`이면 기조우끼리, `R = 0`이면 미조우끼리 균등 선택합니다. 후보 한 명이면 100%, `U = R = 0`이면 추첨하지 않습니다.
- 기조우를 선택한 뒤에는 날짜·같은 세션 제외 규칙이 다시 적용됩니다. 가중치가 제외 조건을 우회하지 않습니다.
- 만남 여부·최근 조우 시각·세션 내 이력은 Encounter 로그를 원본으로 계산합니다. HashSet은 조회 보조 수단이며 영구 로그나 EncounterAvoidance를 대체하지 않습니다.
- 가중치·`U`·`R`·`cooldownUntil`·조우 횟수를 별도 컬럼으로 저장하지 않습니다.
- 가중치 식은 **우선 적용하고 추후 필요하면 변경**합니다. 후보 재검사로 집합이 바뀌면 확률도 달라집니다. 표는 동일 후보 집합에서 한 번 추첨할 때의 값입니다.
- 미조우·기조우를 나누는 이력의 조회 기간은 수식 채택과 별개로 아직 추천 단계이며, 문서 마지막에 남깁니다.

### 9. 탈퇴·삭제와 기록 보존

| 데이터                          | Account 소프트 탈퇴                                                   | Account 사용자 행의 물리 삭제                   |
| ------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------- |
| StudySession / DailyStudyRecord | 같은 탈퇴 시각을 `deletedAt`에 기록하고 일반 조회·집계·제어·재개 제외 | `users.id` 외래키 CASCADE로 삭제                |
| StudySessionRequest             | 보존하되 사용자·세션 삭제 상태로 접근 차단                            | 사용자 또는 연결 세션 삭제 시 CASCADE           |
| Presence                        | 별도 저장 없음, 사용자·세션 삭제 상태로 조회 제외                     | 원본 삭제에 따라 더 이상 조회 대상 아님         |
| Encounter                       | 로그 보존, 기존 인증·삭제 상태로 접근과 신규 참여 제한                | 삭제 계정이 viewer 또는 target인 조우 모두 삭제 |
| EncounterAvoidance              | 관계 보존                                                             | owner 또는 target 삭제 시 해당 관계 CASCADE     |

- Account의 `users.deleted_at` 갱신은 UPDATE이므로 DELETE CASCADE가 실행되지 않습니다. 소프트 탈퇴와 Platform의 세션·일별 기록 삭제 상태 갱신을 연결해야 합니다.
- StudySession·DailyStudyRecord의 정상 기록은 `deleted_at IS NULL`입니다. 물리 삭제는 소프트 삭제 여부와 무관하게 적용합니다.
- Encounter의 viewer 경로는 `users → study_sessions → Encounter`, target 경로는 `users → Encounter.targetUserId`입니다.
- A를 완전히 삭제하면 A가 만난 상대 로그뿐 아니라 다른 사용자의 로그 중 target이 A인 행도 삭제합니다. 익명 계정이나 프로필 스냅샷으로 해당 조우 행을 보존하지 않습니다.
- 세션·조우의 정상 종료, 거절·pass, Pass-by 전환, 다시 만나지 않기는 로그 삭제 사유가 아닙니다.
- 소프트 탈퇴 중 로그 보존이 탈퇴 계정 프로필의 계속 공개를 뜻하지는 않습니다. 표시 방식은 프로필 상세 설계에서 정합니다.
- 사용자 행의 실제 삭제 시점은 Account 정책을 따릅니다. 별도 보관 기간이나 자동 삭제 일정을 추가하지 않습니다. 완전히 삭제된 계정은 조우 후보가 될 수 없습니다.

### 10. 보류된 사항과 후속 설계

#### 보류된 기능·제품 결정

| 항목               | 아직 정하지 않은 범위                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 조우 간격          | 자동 시도 주기·첫 시도 시점·후보 없음 이후 재시도·거절/pass 이후 다음 조우 시점                                                                                    |
| 상대 프로필        | 표시 필드, 최신 프로필과 조우 당시 정보 중 선택, 소프트 탈퇴 계정 표시                                                                                             |
| 조우 로그 화면     | 상대별 묶음·횟수 표시, 개인 설정의 다시 만나지 않기 관리 화면 상세                                                                                                 |
| 가중치용 이력 범위 | 미조우·기조우 판정에 viewer의 전체 보존 조우 이력을 쓰는 방식은 추천안. 현재 세션에서 만난 상대는 이미 후보에서 제외되므로 현재 세션 이력만으로 구분하지 않는 방향 |
| 집중 구간별 이력   | 세션 안의 개별 집중 구간 저장은 현재 범위에서 제외, 추후 필요 시 추가                                                                                              |
| 사용자별 시간대    | 위치·기기별 자동 시간대 및 사용자별 지원은 추후로 미룸. 현재는 `Asia/Seoul` 고정                                                                                   |

가중치 식, visitedAt, EncounterAvoidance, 체류·모드 전환 규칙, Account 완전 삭제 시 로그 삭제 정책은 확정 사항입니다.
가중치의 추후 조정 가능성이 현재 식을 미정으로 만드는 것은 아닙니다.

#### 후속 API·DB·클라이언트 구현 계약

- StudySession: HTTP / WebSocket 등 heartbeat 전송 방식, API 경로·응답·오류, 서버 시각 보정, 기기 전환 배너의 응답 계약과 기존 기기에 전환 사실을 전달하는 수단.
- 저장 대기: 로컬 보관 형식·범위, 앱 재실행 후 복구·재전송 흐름과 오류 표시. 동일 `requestId`·원래 세션/토큰 유지와 오프라인 시간 소급 금지는 확정입니다.
- 공통 구성: 패키지 버전·DataSource·Migration 명령, 만료 작업 실행 주기·운영 구성, 인증 계약의 실제 export 경로·공통 오류 형식. 공통 DB·Migration·`synchronize: false` 원칙은 유지합니다.
- Presence: 조우 응답에 포함할지 조우 시 별도 호출할지, 관리자 조회 경로, 초기 조회·재시도의 활성 조우 권한 확인, 실패·로딩 표시. 상시 상태 갱신을 추가하는 논의는 아닙니다.
- Encounter: 구체적인 API 응답, 방문·거절·pass의 소유권·요청 중복 방지, viewer별 활성 한 건 보장을 위한 잠금·제약, Pass-by 전환에 따른 여러 활성 조우 종료의 일관성·화면 전달.
- Account 설정·조우 테이블: 물리 테이블명·Entity 연결, 계정 전체 조우 이력의 조회 최적화와 관련 인덱스를 구현 계약에서 맞춥니다.

#### 아직 추천 단계인 세부 처리

- 방문 기한 경계: 조우 변경을 직렬화한 뒤 실제 처리 시각 `t < decisionDeadlineAt`일 때 수락하고, `t >= decisionDeadlineAt`이면 미방문 조우를 자동 pass하는 안을 추천합니다. StudySession의 **정확히 600초까지 재접속 허용** 규칙과 별개입니다.
- 조우 계산 상태: `endedAt` 존재, viewer 세션 종료 또는 미방문 대기 기한 도달이면 `ENDED`, 그 외 `visitedAt` 존재이면 `VISITING`, 나머지는 `WAITING`을 추천합니다. API 상태 이름은 후속 확정하며 DB에 별도 상태를 중복 저장하지 않습니다.
- 동일 세션·상대 중복 방지: `UNIQUE (viewer_session_id, target_user_id)`를 추천합니다. 같은 상대 재조우 금지는 확정이며, 서로 다른 두 상대의 동시 활성 방지는 별도 잠금·제약으로 보장해야 합니다.
- 기기 전환 후 기존 앱에는 제어 중지와 전환 안내를 표시하는 방식을 추천합니다. 서버에서 이전 토큰을 차단하는 규칙은 확정입니다.
